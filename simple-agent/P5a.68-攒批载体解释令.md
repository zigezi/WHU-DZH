# P5a.68 攒批载体解释令：批量可以，造尸不行

日期：2026-10-14
性质：对 P5a.65 §四 / P5a.66 §二 / P5a.67 §四 的解释令，回应"小批量积累任务先过线"之议

## 一、裁决

**批量的形式不违禁，违禁的是任务的来源。** 区分标准只有一个——任务价值检验：

- **合规**：批量执行 backlog 中的真实工单（ring_draft 联调、金丝雀门 v1、治理缺陷成册、backlog.md 活清单、E2 规划等）。它们有独立项目价值，尸体是副产品。批量跑、加速跑，都允许。
- **违禁**：为凑 30 具而设计"容易死"的任务（难编译的依赖、易错的迁移、故意长程的操作）。此类批次无论多小，一律不许。

## 二、为什么这不只是省 token 的问题——校准毒化

a65 §四的禁令理由需要补强一条，此前未写明：

代码尸体库是 Phase 1 再校准的**已知答案集**，也是器官分诊尺的刻度来源。**死因类的分布必须反映操作者在真实工作中的真实死法**。人造"易死任务"批次会把死因分布扭成我们选择去诱发的那几类——器官将校准到一个虚构的操作者身上。这与 a62 我在 τ 陷阱富集批上犯的越界是同一类错误（选择性样本当总体证据），只是方向相反：那次是拿偏样本下结论，这次是拿造样本做刻度。

**触发线（30/3）是校准质量门，不是进度条。** 用人造尸体冲线，形式上过了线，实质上拆了线要保护的东西。

## 三、合规的加速器

攒批速率 = 真实工程速率。想快，旋钮是"每天多干真实工单"，不是"造会死的任务"。当前队列（a67 §四）：ring_draft 联调上线 + 金丝雀门 v1 harness 为下一批；两者都是成规模的工程活，失败自然发生，收割器自动在场。

## 四、重申现状

代码尸体 6 具 / 4 类（类的腿已达标，欠量）；τ 封线背景中；触发线未达前，代码域无任何资产出生。
