# P5a.42 — E 门审查裁决与形态再匹配整改令

> 触发：opencode 提交 E 门材料（commit 222fd78 / 远端 215304b），用户转呈全文。
> 裁定：**E 门缓签**。两项零 token 整改（R1 形态再匹配、R2 分母对账）通过后由裁决人复核直接签发 e8 运行令，无需用户再审。一项平行核查（R3 提取保真 85 例）不挡门，与 e8 运行并行，结果作为 e8 判读附件。

## 一、组成分析验收（P5a.41 工单完成，先回答"多少完成、多少成功"）

**任务集（135）按 GT 动作类型**：state_change 108（80.0%）/ read_only 18（13.3%）/ correct_refusal 9（6.7%）；airline 拒绝型 7/41（17.1%），retail 2/94（2.1%）。

**注入池按结尾动作**：PASS-only 池 300 条中 state_change_end 151（50.3%）/ transfer_end 97（32.3%）/ query_end 52（17.3%）。

**裁决人判读**：

1. **"只会无脑转人工"的担忧在任务层面不成立**：80% 的任务质量压在实质状态变更上，正确拒绝仅 6.7%。e7 的 71.9% 通过率中，拒绝型任务顶天贡献 ~6.7pp——通过率的主体是"完成"，不是"会拒"。城堡里有人。
2. **用户直觉在注入池层面部分成立**：三条成功骨架里有一条（32.3%）以 transfer 结尾。池子的"成功经验"有三分之一是拒绝形状——这正是 P5a.41 §三 Δ2 骨架分解条款存在的理由，条款维持，措辞纪律不变。
3. **P5a.41 §四.2 的 E2 升级条款按条件回调**：该条款的触发语境是"若 τ 完成型占比低"。实测 80%，条件不成立——**τ 仍是合法的规划试验场**（多步状态变更任务即 R-105 类是规划的真实需求场）。E2 维持 e8 后高优先，但立项理由从"τ 不够用"改为"真实长程任务的泛化验证"。数据改了结论，登记在案。
4. **50.3% vs 50% 触发线**：分层抽样的强制条款未触发（50.3% ≥ 50%），按预注册字面执行，不追加强制分层。但两臂实测构成失衡（见 §二.R1），借 R1 整改一并修复——**跑前的一切调整都是设计，跑后的任何调整都是犯规**。

## 二、E 门审查发现

**达标线复核（材料 §1/§2/§6）**：top-1 0.034 ≤0.15 ✓；distinct 60 ≥20 ✓；同域 95.6% ≥60% ✓；all_pass ✓；k=3、seed=e8-20260929、near_jaccard=0.6 记录齐全 ✓；proof_fails=0 ✓。此部分全部通过。

**R1（挡门）：两臂形态失衡，违反 P5a.30 §五形态匹配规格。**

- 长度：sibling 均值 7.9（min 2 / max 24，n=43）vs unrelated 均值 4.7（min 1 / max 14，n=44）。均值差 3.2 步，超出"长度 ±2"规格；上限 24 vs 14，分布形状亦不同。
- 骨架类型构成：sibling {SC 58.1%, transfer 30.2%, query 11.6%} vs unrelated {SC 40.9%, transfer 29.5%, query 29.5%}。SC 占比差 17.2pp，query 差 17.9pp。
- **危害**：Δ2 = sibling − unrelated 的全部设计意义是"形态对齐后的纯内容对比"。当前形态不对齐，Δ2 测出的将是"长计划 vs 短计划"与"完成骨架 vs 查询骨架"的混合物——e3–e7 语义不明的老病在最后一道门前复发。E 门存在的意义就是在烧 10M token 之前拦住这种东西。
- **整改令（零 token）**：仅重抽 unrelated 臂注入物（任务↔臂分配不动，随机化完整性不受影响）。规则：(a) 长度分箱直方图（1–3 / 4–6 / 7–10 / 11+）与 sibling 臂逐箱差 ≤10pp，且均值差 ≤1.0；(b) 结尾动作三类构成逐类差 ≤10pp；(c) 重抽算法确定化、新 seed 记录、一次性出结果——**禁止" reshuffle 直到好看"**，一次成稿，好与坏都发表；(d) 新矩阵哈希 + 变更清单（哪些任务的注入物换了）入证据；(e) 其余达标线（top-1/distinct/同域/all_pass）重抽后重算并仍须通过。

**R2（挡门）：分母对账。**

- 材料内部数字不能互相推出：全池 443；结尾动作分类合计 82+259+109=**450**；剔除 185 非 PASS 后应为 258，但 PASS-only 池报 **300**；sibling 臂 45 任务但长度表 n=**43**。
- **整改令（零 token）**：一张分母台账——每个数字注明快照、过滤条件、口径（沉积 run 数 vs 计划条数 vs distinct 注入物数），从原始库到冻结矩阵逐级可对账。同表确认：sibling 臂 45−43=2 例的来源（k=3 耗尽/降级链终止→ineligible 记录）；**预注册 ITT 条款：ineligible 任务仍按所分臂进入分析（assigned = analyzed），不得剔除**，以防脱落偏倚。附一句说明 not_in_static_dict=122 的成分（一句话即可）。

**R3（平行核查，不挡门）：提取保真 85 例。**

- opencode 自查上报计划工具数与源 run tool_call 数不一致 85 例，并主动提议专项核查（疑点：`_store_precedent` 截断）。**此主动上报与上次自抓排序 bug 同类，记为协议健康度正证据。**
- **为何不挡门**：计划与轨迹的计数差若系统性存在，对 sibling 与 unrelated 两臂同构偏置——不污染 Δ2 的内部效度；它威胁的是"注入物=成功经验的忠实蒸馏"这一解释层叙事与 B-3 溯源层。
- **核查令（零 token）**：85 例按方向分类（plan>run 扩张 / plan<run 截断）、按 epoch 分布（示例 8 例全在 e3，须确认是否 e3 集中）、判定计划性质（前瞻性意图 vs 回溯性抽取）。若判定为回溯性抽取且计数系统性不符 → 升级为溯源缺陷，挂 B-3。结果作为 **e8 判读的强制附件**与 Δ2 报告同呈。
