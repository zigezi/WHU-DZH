## 一、工单 1 判决：我的 a27 §4.2 时序规则被证伪，接受；但驳回其假二选一

### 1.1 接受证伪
a27 我立"首个 modify_* 调用解析时点火，宁早勿晚"。回测数据：损害点 = 首次 items 修改调用本身（锁在该调用生效时扣上），"首个 modify 严格早于损害点"= **0/12，可救回 0%**。工具流上的任何谓词都点不到损害点之前——因为损害点就定义在第一个工具调用上。**数据赢，规则撤销。这是本回路第三次兜住仲裁人（P5a.19 对称噪声、a26/a27 任务级 SE、本次时序），全部公开入档。**

### 1.2 驳回"只能 (a) 语义分类器 或 (b) 强制重规划拦截器"的二选一
opencode 漏了两条确定性路径，其中一条架构成本为零，一条恰好落在 monitor 的法定职权内：

- **路径 A（零新架构，立即可回测）**：任务开始时（现有 messages.insert(1) 通道）用**请求文本关键词谓词**点火——请求同时含地址类与物品类修改意图 → 注入锁序规则。确定性函数、无 LLM、无新通道。代价是漏检率（措辞不含关键词时漏）——但漏检率恰好在 e4-e6 请求文本上可回测量化，这正是 a25 §五的门所要求的动作，不是死结。
- **路径 B（正式解法，monitor 职权内的执行期拦截）**：**调用前拦截器**——monitor 在 `modify_pending_order_items` 即将执行且同订单 `modify_pending_order_address` 尚未调用时，于该次工具结果内附加条件式提醒（"若还计划改地址，先地址后物品"）。触发器纯结构（工具名 + 调用历史谓词），**点火在执行前 = 损害点前**；规则文本带条件，语义判断仍归 worker，拦截器不做语义判断。无需"强制重规划"，一次提醒而已。误报成本 = 每订单至多一次短提醒。

**裁决：路径 B 为锁序资产的法定实现形态；路径 A 为工程受阻时的降级方案，其漏检率回测作为 B 的参照基线。**

### 1.3 立法：执行期确定性拦截通道（新能力类别，受治理）
本次裁决确立一个新的架构能力类别，边界如下：
1. 通道所有权归 **monitor**（纯规则职权不变——拦截触发器必须是确定性谓词，禁止 LLM 参与点火决策）；
2. 实现形态：包装工具执行层，谓词命中时向**该次工具结果**附加资产文本（与 opencode 源码中"read 时附加目录级 AGENTS.md"同构——市面范式里唯一的确定性注入，恰好也是这个形态）；
3. 入住资格：只有通过金丝雀电池（B-2）且持有效信用级别的 L2 资产可占用拦截通道；每次点火记 span（MR-8）；
4. 拦截通道的资产部署本身按 P5a.23 走同轮 A/B（拦截 on/off 任务级随机）——**锁序拦截器的验证实验登记为 e9 候选**，排在 e8 之后。
